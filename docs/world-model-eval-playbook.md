# 世界模型评测方法手册（面试版）

> 底稿：夕小瑶《实测 5 款国产世界模型，看清「生成世界」走到了哪一步》（2026-09-14）
> 本文在原文的实测案例上，补齐真实评测工作里的设计、口径、数据结构与质检。
> 阅读顺序：0 → 1 → 2 是"我怎么看这篇稿子"；3 之后是"我自己会怎么做"。

---

## 0. 一页摘要

原文做的是**体验式横评**：同题投喂、并排看片、用文字下结论，不给总分。
它回答的是"现在能玩到什么程度"。

真实评测工作还要回答另外三个问题：

1. **同一件事，谁更好、好多少？** → 维度锚点 + GSB 相对胜负
2. **这个结论可不可复核？** → 盲测、证据时间戳、JSON 留痕、质检
3. **这个结论能推广到哪？** → 样本量、不可比声明、成本口径

本文把这三点补上，并给出一条能落地的流水线。

---

## 1. 原文是怎么测的

一句话：**先按能力分赛道，再在同赛道里同题对比，最后用序关系而不是分数下结论。**

- 选手：LingBot-World 2.0（蚂蚁）、Zing-0.5（Loopit，开源）、HappyOyster 1.0（阿里）、R1（爱诗）、HY-World 2.1（腾讯混元）。
- 能力三分：**漫游**（自己走）、**导演**（下指令让世界变）、**联合控制**（边走边改）。
- 明确不排总分："功能有多少，和做得好不好，是两回事"，"能同题的放在一起测，玩法不同的单独说"。
- 八道题：输入还原 → 运动后一致性（主体/环境）→ 物理合理性 → 漫游控制 → 导演能力 → 联合控制 → 响应速度 → 成本。
- 结论形态：`Zing = HappyOyster > LingBot`、`HappyOyster > Zing > LingBot`、`三家五五开`。

**原文结论速查**

| 维度 | 结论 |
|---|---|
| 输入还原度 | Zing = HappyOyster = LingBot；爱诗把背影转成正脸；混元拒收人像 |
| 主体一致性 | Zing ≈ HappyOyster > LingBot；爱诗换了三张脸 |
| 环境一致性 | HappyOyster > Zing > LingBot（LingBot 星空退化成蓝条纹） |
| 物理合理性 | Zing 更胜（海啸从海面来、天亮渐变） |
| 漫游控制 | Zing 更跟手，LingBot 镜头贴背，整体五五开 |
| 导演能力 | HappyOyster 最会把局部过程演清楚；Zing 擅续演；LingBot 易混物体；爱诗易飞 |
| 联合控制 | 仅 Zing / LingBot 可比；Zing 空间关系更清楚，LingBot 特效遮挡 |
| 响应速度 | 环境变化 Zing > LingBot > 爱诗；漫游三家五五开 |
| 成本（10 分钟） | LingBot ≈ $1.98；HappyOyster ≈ $10.40（含建世界）；Zing 自部署 ≈ ¥1 以内 |

## 2. 原文的长处与缺口

| 原文做得好的 | 真实工作还缺的 | 补法 |
|---|---|---|
| 先分能力再对比，拒绝硬排总分 | 缺"分维度分数"，只有序关系 | 每维 1/3/5 三档锚点 |
| 同题同图同 prompt | 没写死时长/分辨率/控制脚本/录屏规格 | 条件清单 + 落库 |
| 用 GIF/视频做证据 | 证据没有时间戳，无法定位 | `evidence_ts` |
| 诚实标注"无法同题排名" | 工作台没有"N/A 不可比"这个选项 | 允许 `-` 并强制备注原因 |
| 成本单列一节 | 口径混（自部署成本 vs 用户账单） | 统一到"每次会话" |
| 结论克制 | 没有样本量、没有一致性检验 | N 声明 + 双人分歧率 |

一句话：**原文是好的"评测报道"，还不是"评测数据"。**

## 3. 评测设计

### 3.1 先切能力，再谈分数

世界模型不是同一类产品，直接总分排名会失真。先做能力矩阵：

| 能力 | 定义 | 判定方式 |
|---|---|---|
| 输入还原 | 首帧是否沿用参考图的主体/构图/关系 | 首帧与参考图并排 |
| 漫游 | 按键→位移/转向是否对应 | 固定按键脚本，看是否跟手 |
| 导演 | 文本指令能否演成有前后关系的过程 | 一条故事线 + 中途追加指令 |
| 联合控制 | 移动、视角、环境变化同时发生 | 边按 W 边下指令 |
| 响应 | 输入到画面变化的延迟 | 计时 + 逐帧数 |

只有**能力同时具备**的两家才进同一张对比表；能力缺失记 `N/A`，并在报告里写原因（产品不支持 / 入口拒收 / 未开放）。

### 3.2 三条不可比规则

1. **能力缺失不可比**：爱诗不能漫游，就不进漫游表，不给他打低分。
2. **入口限制不可比**：混元拒收人像图，属于产品约束，不是模型能力差；换纯风景图另开一组。
3. **模式不可比**：HappyOyster 的漫游与导演是两个入口，不能算"联合控制"；联合控制表里只能有 Zing 和 LingBot。

> 这一条是面试里最容易加分的：**能说清"什么不能比"，比多测两个 case 更显专业。**

### 3.3 同题条件锁死清单

每次对比必须记录，缺一项结论就不可复核：

- 同一张参考图（存 sha256，不存文件名）
- 同一段 prompt（存 `prompt_id`，改一个字就是新 case）
- 同一有效时长（秒），不是同一帧数
- 同一分辨率与画幅
- 同一控制脚本（按键序列 + 每段秒数 + 是否手动）
- 同一录屏规格（分辨率 / 容器帧率 / 是否插帧）
- 同一评分口径（同一版锚点表）

## 4. 维度与 Rubric 锚点

### 4.1 七个维度

| # | 维度 | 一句话 | 主要看什么 |
|---|---|---|---|
| 1 | 输入还原 | 首帧像不像参考图 | 主体、构图、遮挡关系 |
| 2 | 主体一致性 | 走一圈回来，主体还是不是它 | 人脸/服装/车体是否漂移 |
| 3 | 环境一致性 | 转一圈回来，空间还在不在 | 建筑、星空、家具是否变形/新增/消失 |
| 4 | 物理合理性 | 变化符不符合物理 | 水从哪来、光怎么变、有无穿模 |
| 5 | 漫游控制 | 按键是否跟手 | 位移方向、转向、镜头距离 |
| 6 | 导演能力 | 指令能否演成过程 | 动作因果、镜头是否为叙事服务 |
| 7 | 响应速度 | 输入到画面变化的延迟 | 首帧响应、指令生效延迟 |

### 4.2 1 / 3 / 5 锚点

| 维度 | 1 分 | 3 分 | 5 分 |
|---|---|---|---|
| 输入还原 | 主体/机位明显错位 | 大体一致，细节有偏 | 主体、构图、遮挡关系一致 |
| 主体一致性 | 换脸/换装/主体崩坏 | 轻微漂移，可辨认 | 全程稳定，细节保持 |
| 环境一致性 | 场景重构、物体消失 | 局部形变，主要结构在 | 转回原位，布局与光照一致 |
| 物理合理性 | 穿模、漂浮、无碰撞 | 小瑕疵，整体可信 | 碰撞、重力、材质、光源一致 |
| 漫游控制 | 视角失控、方向相反 | 可动但有漂移/延迟 | 跟手，视差正确，距离稳定 |
| 导演能力 | 不响应或答非所问 | 元素出现，但关系乱 | 动作有因果，镜头服务叙事 |
| 响应速度 | >3s 或需要重试 | 1–3s | <1s，连续操作不断档 |

评分规则：
- 只对**动作**打分，不对"好不好看"打分；"好看"是 T2V 的单帧美学维度，不是这里。
- 看不清就留空，不猜。
- 每个分数必须配至少一个 `evidence_ts`。
- **只用 1 / 3 / 5 三档**：上表只给了 1、3、5 的判据，2 分和 4 分没有定义。没有定义的档位会被评分者各自发明标准，同一段视频两个人能差一分却没有可争论的依据——那一分是噪声。

**为什么不自造五档（公开资料核查，2026-11）**：

| 来源 | 公开的评测口径 | 是不是人工 1–5 量表 |
|---|---|---|
| Hy-Nomas（arXiv 2610.36729，腾讯混元，2026-10） | 正文只说"human evaluation 中优于现有世界模型" | 否，未披露量表与档位 |
| WorldMark（Alaya Lab，arXiv 2604.21686） | 9 个确定性指标归一化到 0–100 | 否，是自动指标，不是 Likert |
| Happy Oyster / "0 Bot World" | 未检索到可核实的评测论文 | 无 |

结论：没有可照抄的公开人工量表。既然锚点只写了三行，就用三行；要补分辨率就靠 GSB 的相对胜负和证据时间戳，而不是把 2/4 的刻度硬造出来。

### 4.3 能力轴与质量轴不要混

- **能力轴**回答"能不能"：有没有漫游、有没有联合控制。
- **质量轴**回答"好不好"：1/3/5 三档（只有 1、3、5 有锚点定义，2/4 无定义故不用）。

把两件事塞进一个总分，会出现"功能多但都做得很差"却排第一的情况。正确做法是**先按能力矩阵分组，再在组内比质量分**。

## 5. GSB：相对胜负

### 5.1 为什么 Rubric 不够

Rubric 是绝对分，适合定位失败、判断能不能用；GSB 是相对胜负，适合回答"这版比上版好吗"。

真实迭代里两个都要：

- 只看 GSB → 丢掉绝对质量，"两个都很差但一个稍好"也会被记成赢。
- 只看 Rubric → 看不出相对提升，分数还会随评分人漂移。

### 5.2 判定与公式

- **G（Good）**：A 明显更好
- **S（Same）**：持平，或差异不足以影响使用
- **B（Bad）**：B 明显更好

```
净胜率 = (G − B) / N
去平局胜率 = G / (G + B)
```

报告里两个都写：净胜率回答"整体赢面"，去平局胜率回答"有差异时谁赢"。

### 5.3 盲测流程

1. 同 case 两条视频，随机绑定 A/B，评分人不知道对应模型。
2. 两侧各自独立打 Rubric，先不看对方。
3. 打完再给整体 G/S/B。
4. 全部 case 评完，一次性揭盲。
5. 揭盲后不改原始分，分歧写进 notes。

### 5.4 N 小时的报法

N ≤ 10 时，只报"案例研究"，不写"全面领先"。

可以写：
> 在 6 个相机路径 case 上，A 在 4 个 case 的相机控制维度高于 B，2 个持平；样本量不足以支持总体结论。

不要写：
> A 的相机控制显著优于 B。

## 6. 一条完整流水线（以 B2-0001 为例）

| 步骤 | 动作 | 产出 | 验收 |
|---|---|---|---|
| 1 选 case | 8s 相机路径：抬 2s / 压 2s / 左 2s / 右 2s | `case_id` | 有预期与失败模式 |
| 2 锁条件 | 参考图、prompt、时长、分辨率、控制方式 | `conditions` | 三项以上可机器校验 |
| 3 录制 | 首尾各垫 2s，不剪接，一镜到底 | `out/<model>/<case>.mp4` | 时长、帧数、分辨率达标 |
| 4 打 Rubric | 双人独立，四维 1/3/5，标 `evidence_ts` | `scores.jsonl` | 无越界、无缺项 |
| 5 打 GSB | 盲测 A/B，先评后揭 | `gsb.jsonl` | `blind_map` 一致 |
| 6 质检 | 跑规则脚本 | `qa_report.json` | 0 error |
| 7 归因 | 每个低分格写现象→机制→复现 | `badcase.md` | 可复现 |
| 8 汇总 | 按维度出表，不合成单一总分 | `report.md` | 含 N 与边界 |

关键点：**Rubric 与 GSB 是两套数据，不要互相覆盖。** 工作台上"两侧各自打分 → 整体单选 → 揭盲"，对应的就是这条。

## 7. 数据结构与质检

### 7.1 三层数据

```
case    → 案例：条件、预期、失败模式
run     → 一次生成：模型、入口、会话时长、成本、文件哈希
score   → 一次评分：评分人、维度分、证据时间戳、置信度
```

三层分开的好处：换模型不用改 case，换评分人不用改 run，重跑质检不用重录。

### 7.2 schema 示例

```json
{
  "case_id": "WM-CAM-001",
  "task_type": "camera_path",
  "conditions": {
    "init": "image",
    "init_sha256": "…",
    "prompt_id": "p01",
    "duration_sec": 8,
    "fps": 16,
    "resolution": "960p",
    "control": "manual",
    "control_script": ["up:2", "down:2", "left:2", "right:2"]
  },
  "runs": [{
    "run_id": "r-001",
    "model": "lingbot-world-2",
    "entry": "reactor",
    "session_sec": 142,
    "cost_usd": 0.99,
    "video": "out/lingbot/WM-CAM-001.mp4",
    "sha256": "…",
    "frames": 128
  }],
  "scores": [{
    "rater": "r1",
    "model": "lingbot-world-2",
    "instruction": 4,
    "physics": 3,
    "camera": 2,
    "memory": 3,
    "evidence_ts": [1.8, 3.1, 6.4],
    "confidence": "high",
    "notes": "左移段视角漂移，回程未回到原位"
  }],
  "blind_map": { "A": "lingbot-world-2", "B": "hy-nomas" },
  "gsb": { "rater": "r1", "verdict": "B", "reason": "B 回程位置更准" }
}
```

### 7.3 质检 12 条

| # | 规则 | 级别 |
|---|---|---|
| 1 | `case_id` 在 cases 清单中存在 | error |
| 2 | `model` 在允许名单内 | error |
| 3 | 分值 ∈ {1,2,3,4,5} 或 `-` | error |
| 4 | 能力缺失必须是 `-`，不能填 3 | error |
| 5 | `evidence_ts` ⊆ [0, duration] | error |
| 6 | 视频文件存在且 sha256 匹配 | error |
| 7 | `frames` ≈ duration × fps（±1） | warn |
| 8 | `blind_map` 与 `gsb` 的 A/B 一致 | error |
| 9 | 同 case 同 model 只允许一条 final run | error |
| 10 | 每个 case 至少两名评分人 | warn |
| 11 | 实际时长与声明时长偏差 >0.2s 必须写 notes | warn |
| 12 | 付费入口必须填 `cost_usd` 与 `session_sec` | error |

### 7.4 一条质检输出

```json
{
  "checked": 18,
  "errors": [
    {"row": 7, "rule": 4, "msg": "B1 无 camera 能力，camera 应为 '-'，实际为 3"}
  ],
  "warnings": [
    {"row": 12, "rule": 11, "msg": "声明 8.0s，实测 8.4s，notes 为空"}
  ]
}
```

质检不是形式主义：**上面第 4 条能直接抓出"给不支持的能力硬打分"这种最伤可信度的错误。**

## 8. 一致性检验

- 同一片两人独立评，先各打各的，再对差异 ≥2 分的格子讨论。
- 报告里写分歧率：`分歧格数 / 总格数`。
- 有条件时算 Cohen's kappa；样本小就只报分歧率，不硬算。
- 讨论后不改原始分，另存 `consensus` 字段，保留可追溯性。

## 9. BadCase 归因

每条 low score 收敛成四段：

1. **现象**：什么时间、什么画面、什么动作下发生
2. **机制**：模型能力 / 交互设计 / 平台与网络
3. **复现条件**：同样的按键序列、同样的时长、是否稳定复现
4. **证据**：`evidence_ts` + 帧号 + 片段文件

三类机制要分开，否则会把平台问题算到模型头上：

| 机制 | 例子（原文） | 归属 |
|---|---|---|
| 模型能力 | LingBot 车底突然露出四个大黑轮胎 | 模型 |
| 模型能力 | 爱诗同一个角色换三张脸 | 模型 |
| 模型能力 | LingBot 星空退化成蓝色横纹 | 模型 |
| 交互设计 | HappyOyster 画面下缘突然伸出两只手 | 交互/视角设计 |
| 平台 | 混元拒收人像图 | 产品约束，非模型质量 |
| 网络 | 响应慢、卡顿 | 需重测排除 |

## 10. 成本口径

成本必须写清四件事，否则数字没有意义：

1. **入口**：官方站 / 托管平台 / 自部署，价格不同
2. **计费单位**：按秒、按分钟、还是按次
3. **是否含空转**：实时世界模型从 ready 就开始计费，你调 prompt 的时间也算钱
4. **是否含一次性费用**：建世界、上传、存储

统一口径建议用"**一条 8 秒片段的实际会话成本**"，而不是"8 × 单价"：

```
单条成本 = 会话时长(sec) × 单价($/sec)
```

对照原文（价格快照以当天页面为准）：

| 模型 | 公开单价 | 10 分钟纯会话 | 单条 8s 片段的实际成本 |
|---|---|---|---|
| LingBot-World 2.0 | $0.007/s（$0.42/min） | ≈ $4.20 | 约 $0.4–1.3（会话 1–3 分钟） |
| HappyOyster 1.0 | $0.0278/s（$1.668/min） | ≈ $16.68 | 约 $1.7–5.0 |
| Zing-0.5 | 团队披露 ¥0.06/min 推理成本 | ≈ ¥0.6 | 不可直接当用户账单 |

> 原文写 LingBot 10 分钟约 $1.98，与当前官方页 $0.42/min 对不上。这类差异在报告里必须标注"价格快照日期 + 入口 + 是否含平台费"，不能直接引用。

## 11. 工作台怎么接

现有页面已经覆盖的部分：

- **方法页**：三层结构（标注→评测→归因）、GSB 公式、Rubric 1/3/5 锚点、四维/五维/六维定义。
- **世界模型页**：A/B 盲测、两侧独立 Rubric、整体 G/S/B、揭盲、同位姿对照、证据时间戳、失败模式备注。
- **数据页**：案例→输出→标注→结果四层、JSON schema、runs.json。
- **BadCase 页**：现象→归因→复现条件→证据。

还缺的四块（也是面试官最容易追问的）：

1. **真实录屏**：当前是占位，一问"你自己跑过吗"就露底。
2. **N/A 与不可比**：页面只有 A/B 两栏，没有"该模型不具备此能力"的选项。
3. **统计与一致性**：没有分歧率、没有 N 声明。
4. **成本列**：评分表里没有会话时长与金额。

最小补法：选 1 个 case × 3 家，跑通"录屏 → 双人打分 → GSB → 质检 → 归因"整条链路，把真实数据填进页面。**一条真数据胜过十页设计。**

## 12. 边界声明

- 本文档是**方法层**复用，实测结论归属原文作者；不要把自己的复现说成原创实测。

## 附录 A：面试 3 分钟讲法

1. **先讲判断**：世界模型不能排总分，要先按能力分赛道（漫游/导演/联合控制），再在同赛道内比。
2. **再讲口径**：同图、同 prompt、同时长、同控制脚本、同录屏规格；能力缺失记 N/A，不硬打分。
3. **再讲证据**：每维 1/3/5 三档锚点 + `evidence_ts`；Rubric 打绝对，GSB 打相对，盲测先评后揭。
4. **再讲可复核**：三层 JSON（case/run/score）+ 12 条质检，能抓出"给不支持的能力打分"。
5. **最后讲边界**：N 小只做案例研究；成本按会话算不按秒算；公开结论归属原作者。

一句话收尾：**我不是做了一个好看的评测页，我是把"评测结论能不能被复核"这件事做进去了。**
